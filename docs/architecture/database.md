# Database Architecture

## Engine

- PostgreSQL 16 (containerized via `docker-compose.yml`)
- Bootstrap SQL: `init.sql` mounted to `/docker-entrypoint-initdb.d/init.sql`
- `init.sql` should stay bootstrap-only (grants/extensions), not app table DDL.

## Schema Revisions / Upgrades

- SQL migration files live in `python/mp/db/migrations/` and are named like `0001_description.sql`.
- These migration files are the single source of truth for app schema.
- On API startup, `python/mp/db/upgrade.py`:
  - ensures `app_config` exists,
  - ensures `app_config['dbversion']` exists (default `-1`),
  - reads current revision from `dbversion`,
  - applies all missing migration files in numeric order,
  - updates `dbversion` after each migration.
- This supports in-place schema upgrades without wiping the Postgres volume.
- Users can opt into seeded demo data via `users.example_data`; startup sync fills missing example records for opted-in users.

## Core Tables (Current)

- `accounts`
- `pending_payments`
- `contracts`
- `payables`
- `funds`

## Schema Characteristics

- Primary keys are integer IDs but are not auto-generated by sequences in current DDL.
- Most money fields are stored as integer cents (`BIGINT`), not decimals.
- Timestamp columns exist but are not defaulted/populated automatically in DB layer.
- Foreign key relationships are documented in comments but not enforced as DB constraints yet.

## Access / Permissions

- `init.sql` grants DB/table/sequence permissions to app user.
- API connects via `DATABASE_URL` from compose env wiring.

## ORM Relationship

- SQLAlchemy model currently exists only for `accounts` (`python/mp/schema/account.py`).
- If schema changes are made, update both:
  - SQL DDL in `init.sql`
  - Python ORM/Pydantic models in `python/mp/schema/`

## Operational Notes

- Data is persisted in named volume `postgres_data`.
- Recreating DB from scratch requires dropping volume (`docker compose down -v`).
